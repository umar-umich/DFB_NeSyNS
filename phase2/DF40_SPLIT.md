# Stage 0.1 — DF40 Dev / Holdout split (SEALED 2026-08-20)

Machine-readable copy: `configs/discern_v2/df40_split.json`. Every method, video count and
resolution rate below was read from that file, which was generated by walking the DF40 JSONs and
checking frames on disk.

**The rule.** A method in Dev can never move to Holdout. No configuration, gate, threshold or
promotion decision may read a Holdout number before Stage 8.

---

## What must be said about this split in the paper

The brief asks Holdout to carry a zero-shot claim. It can, but only with a precisely stated
guarantee, and stating it loosely would be false.

Phase 1 produced `analysis/discern_v2/A1_complementarity/DF40/auroc_per_generator.csv`, a
**per-generator AUROC table over 70 DF40 generators** — effectively the whole corpus. Under the
strictest reading of "already inspected during Phase 1", every DF40 method is Dev and there is no
Holdout at all.

Two things narrow that, and both are checkable:

1. **Those numbers were computed on DiCoME's operators**, not on DISCERN V1. The columns are
   `P0-DS, P1a, P1b, P1c, P1d, P2a, P3a, P4`. V1's three branches (`sem`, `ref`, `proc`) have
   never been scored per-DF40-method by anything — DF40 is absent from the V1 per-sample export
   (`logs/v1/eval/epoch_007_gated_diverse/`, 7 sources, no DF40 rows).
2. **The decision those numbers drove is not in V1.** They selected a manifold projector
   (`training/config/discern_v2/_base.yaml`: `projector: beta_tcvae`, "SELECTED 2026-08-15 by
   Umar, on Track A evidence"). V1 has no manifold projector branch. That contamination flowed
   into the D-ladder, not into the system this brief builds on.

   **The one exception, and it matters for Stage 2.** The same note says P1d (MR-VAE) was kept
   for the D4 arm because "P1b's A2a gate recovery is NEGATIVE under the FF++ threshold
   (-0.032 / -0.031) while P1d stays positive (+0.027 / +0.265)" — an A2a number computed on DF40.
   So **P1d's privileged status is DF40-contaminated by construction**, and Stage 2's DF40-Dev
   validation of P1d is a re-test of a hypothesis DF40 already selected. Stage 3 must weigh P1d's
   recovered fraction knowing this; it is not independent evidence.

So the honest wording, which should survive into the paper verbatim rather than being softened:

> DF40-Holdout methods were sealed before Phase 2 began and no Phase-2 configuration, gate,
> threshold or promotion decision read a Holdout number. They are not "never seen": a Phase-1
> per-generator table computed with a different operator family covered most of the corpus.

Anything stronger than that would be a claim the repository contradicts.

## Path-resolver fix made in this stage

At the start of Stage 0, **60 of 81 DF40 method JSONs resolved** and `heygen` — the brief's harm
probe — resolved at **exactly 0.0**, as did both `e4e` arms, `styleclip` and `whichisreal`. None
of that was missing data. `training/dataset/df40_paths.py` was extended and now resolves
**77 of 81**; all nine Dev arms and `heygen` are at 1.000.

Four distinct causes, each confirmed by listing the directory rather than inferred:

| cause | example | fix |
|---|---|---|
| path not recognised as relative at all | `e4e_ff` writes `./deepfakes_detection_datasets/…`; `e4e_cdf` writes the authors' absolute cluster path `/Youtu_Pangu_Security_Public/…` | `_normalise()` strips both prefixes. These two arms scored 0.0 because of two characters at the front of a string, while their frames sat on disk |
| method directory renamed or double-nested | JSON `whichisreal` → disk `whichfaceisreal/whichfaceisreal/`; `heygen` → `heygen/heygen_new/`; `styleclip` → `styleclip/styleclip/`; `rddm` → `RDDM/` | `METHOD_DIR_ALIASES`, each entry confirmed by `ls` |
| source pool named in JSON, product named on disk | `DiT/cdf/Celeb-real/…` → `DiT/cdf/Fake_from_Celeb-real/…`, and `YouTube-real` → `Fake_from_**Y**outube-real` (the capitalisation really does change) | `CDF_SOURCE_DIRS` |
| pre-DF40-namespace layout | `simswap/cdfv2/frames/…` → `test/simswap/cdf/frames/…` | extra candidate in the non-`DF40/` branch |

Resolution is still measured per method and recorded, never assumed — the original 21.6% failure
came from generalising one method's layout to all of them.
